## Screens in this handoff
1. Calendar overview: default Week, Month, List; child filters All/Kai/Aurora; calendar key on desktop.
2. Add Event: type first (Activity, Parenting time, Family event, I'm unavailable), dates/times/all-day, children multi-select (None/some/All), category, location, notes.
3. Event details: parenting time, activity, joint family event, unavailable; pending/confirmed states and relevant actions.
4. Add Task and Task Details: due date, child association, collaborative checklist, per-item completion attribution, required-item progress, per-parent Seen on intentional detail open. Completion celebration only when final required item transitions to complete, respecting reduced motion.
5. Add Reminder and Reminder Details: date/time or all-day, optional child association, details, creator identity, subtle per-parent Seen on intentional detail open. No completion checkbox or task assignment.

All screens must be designed and implemented for mobile and desktop, light and dark, with WCAG AA contrast and 44px interactive targets. Use fictional family only; no real children's photos.

## Critical implementation constraints
- Pending or proposed items must not look confirmed: label and pattern as well as color.
- A joint family event displays both parent avatars and only participating children; both-parent approval is required before confirmation. No custody changes from event acceptance.
- Unavailability is neutral gray and marked “Unavailable”; optional private notes never appear to the other parent. Support recurring blackout edit scopes (one, following, all).
- Single-day events must stay inside their calendar day column; multi-day events span only their actual dates; long labels truncate. No mobile calendar legend and no child avatars in mobile Month cells. Child indicators are permitted inside mobile Week events.
- Calendar empty/loading/error/rejected/locked states, swaps, and approvals inbox remain separate design work under issue #48.

## Proposed elements — NOT automatically approved requirements
Generated images may show attachments, a manually controlled “Requires Approval?” switch, task assignee selector, task-level “Mark as Complete” action, and reminder recurrence/location. These must be reconciled with existing GitHub requirements before Claude implements them. In particular, required approval must follow product rules rather than an arbitrary toggle; task completion must not bypass required checklist items. The task/reminder edit/delete permissions, conflicts and approvals need explicit decisions.

## Owner decisions on the proposed elements (October 21, 2026)
These settle the "Proposed elements" above for v0.3.0:

| Topic | Decision |
|---|---|
| Attachments | **Not in v0.3.0.** They come with uploads and storage in v0.5.0 (#115). Hide every attachment control on the boards. |
| Tasks | **Shared, no assignee.** A task with a checklist completes automatically when its last required item is ticked (with the reduced-motion-aware celebration). A task without a checklist has one **Mark done** action. Every tick and completion shows who did it. No task-level "Mark as Complete" that skips required items. |
| Reminders | **Repeat yes, location no.** Daily, weekly or monthly with an end condition. Things that happen somewhere are events. |
| Edit and delete (tasks, reminders) | **Either parent, at once, no approval.** History shows who changed what, and the other parent sees a quiet "edited by" note. Approvals stay for parenting time, holidays and family events. |

## Owner approvals and corrections (October 20, 2026)

### Request Swap — visual direction approved
- Flow: select an existing parenting-time event → Request Swap → propose replacement dates/times → compare original and proposed schedule → review and send → request-sent confirmation → pending request details.
- The other parent's unavailability triggers a gentle, **non-blocking** warning. Present **Send Anyway** and **Choose Different Dates** as explicit choices. The generated board omitted this exact two-choice presentation; implement the requirement, not the omission.
- Other parent's approval is required; no automatic parenting-time changes before approval.
- Board: `docs/design/assets/calendar/calendar-request-swap-composite.png` (October 21, 2026): select the parenting-time
  event → Request Swap → new date and time with an optional reason → review (current vs proposed) → "Swap Request Sent"
  → pending details with Withdraw. Where it differs from the rules above, the rules win:
  - The unavailable warning on the board is only a note; implement the explicit **Send Anyway** and **Choose Different
    Dates** choices.
  - The board's "approve, decline, or propose a different time" wording: counter-proposals aren't a feature. Say
    "approve or decline".
  - The status timeline's "Updated on calendar" step follows approval automatically; there's nothing to do by hand.

### Approvals Inbox — visual direction approved with corrections
- Show pending requests, original → proposed details, approve, decline with optional comment, withdraw own requests, and History showing approved/declined/withdrawn outcomes with attribution and dates.
- **Do not add Approvals as an eighth sidebar item.** Preserve the approved seven-item sidebar and surface approvals within Calendar.
- Only the receiving parent can Approve/Decline. Only the requesting parent can Withdraw. The board incorrectly mixed these permissions.
- Generated attachment controls and Reply buttons are not automatically approved.
- Proposed composite upload: `docs/design/assets/calendar/calendar-approvals-inbox-composite.png`.

### Joint Family Event Approval — visual direction approved; revised type-selection design preferred
- Flow: Add → choose Event (vs Task/Reminder) → choose event type **Family Event** (vs Activity, Parenting Time, I'm Unavailable) → enter details → review → Send for Approval.
- Family Event selection **automatically** requires both-parent approval. The creator's submission counts as their approval; the other parent explicitly accepts before Confirmed.
- Both parents are **fixed participants**, not selectable checkboxes. Children may be None, some, or All. Do not require any child to attend.
- No separate “Requires Approval?” switch. Pending/declined events must not appear confirmed; acceptance updates the shared calendar automatically, without “Add to My Calendar.”
- Material edits to confirmed joint events (date/time/location/attendees) require renewed approval. No recurring joint events in first version.
- Proposed original composite: `docs/design/assets/calendar/calendar-joint-family-event-approval-composite.png`.
- **Preferred revised reference:** owner-provided prior mockup showing desktop and mobile light/dark with Event/Task/Reminder choice and event-type choice together. Do not substitute later layout experiments.

### Exact selection-box rule — explicitly owner approved, supersedes mockup indicators
Applies to **Add to Calendar / What are you creating?** (Event, Task, Reminder) and **Choose Event Type** (Activity, Parenting Time, Family Event, I'm Unavailable) on **mobile and desktop, light and dark**.
- Each entire card/block is clickable/selectable.
- Selected state: **only the entire block is highlighted** (pale/light sage green in light mode; richer/darker green in dark mode).
- Unselected state: normal neutral surface.
- **No radio buttons, no checkmarks, no circles, no selection glyphs on either side** of these option cards. Keep the original icons identifying each option.
- Do not change the approved layout, spacing, copy, or flow beyond removing selection controls and using block highlight.
- This rule is limited to the two **choice screens**; it does not prohibit functional child-attendance checkboxes elsewhere in the form.
- The user specifically chose the earlier reference mockup over subsequent redesigns. Treat any radio/checkmark shown in that reference as an artifact to remove, not an instruction to implement.

### Unavailability & Recurring Events — visual direction approved (October 20, 2026)
- Owner approved the creation flow and existing layout across desktop/mobile and light/dark: Add → Event → I'm Unavailable → date/time (all-day default) → optional recurrence (repeat days, end condition, occurrence preview) → review and save.
- **Selection rule is mandatory** on all choice cards: tap/click the entire block; selected state uses the existing pale sage green (light mode) or deep green (dark mode). **No radio buttons, checkmarks, or selection glyphs** on the choice cards. Keep the approved layout unchanged.
- Unavailability status is visible to the other parent as **“Unavailable”**; optional reason/private notes are never shared. The image's ambiguous “This will only be visible to you” wording must be corrected.
- Recurring series editing/deletion must offer **This event**, **This and following**, and **All events**. This editing flow is required but not pictured on the approved creation board.
- When a blackout overlaps existing parenting time, show a gentle conflict warning and suggest arranging coverage. Do not change custody or parenting responsibility automatically.
- The other parent's unavailable dates trigger non-blocking warnings on swap requests, as documented above.
- Board: `docs/design/assets/calendar/calendar-unavailability-recurrence-composite.png`.

### Calendar States — visual direction approved (October 20, 2026)
- Owner approved the Calendar States board as sufficient visual direction for desktop/mobile in light/dark mode.
- Empty state: calm copy, no-events illustration, Add to Calendar action.
- Loading state: non-disruptive skeleton placeholders; error state: clear explanation and Try Again.
- Calendar views must be **Week (default), Month, List**, NOT the generated mockup's Month/Week/Day labels.
- Pending/proposed events must use explicit status labels and distinct dashed/hatched patterns, not color alone; confirmed must be unambiguous.
- Declined requests must be identified as declined, and must not look like confirmed events on the shared calendar.
- Unavailable blocks use neutral gray styling and display only **Unavailable** to the other parent; never expose private notes.
- Locked/past events remain readable but are not editable when the product rules prohibit editing.
- Include the special legacy status **“Confirmed before your co-parent joined”**; absent from the generated board, but required by issue #48.
- Keep the approved seven-item sidebar and mobile navigation.
